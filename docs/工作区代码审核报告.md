## JD-001 [P1] 同名下载文件可能覆盖已有媒体

- 确认程度：代码确认；等价 JVM 文件探针已复现并发覆盖和编号耗尽覆盖，未运行 Android Worker。
- 位置：[DownloadWorker.kt · 513](/Users/torahli/github/JellyDroid/core/src/main/java/dev/jdtech/jellyfin/work/DownloadWorker.kt:513)，`resolveFinalFile()`；同文件 `finishDownload():479`、`renameTo():480` 和数据库回写 `:487`。命名来源见 `core/src/main/java/dev/jdtech/jellyfin/utils/DownloaderImpl.kt` 的 `resolveServerFileName()`，唯一 Work 名包含条目和媒体源 ID，不会把不同条目的同名下载串行化。
- 触发：同一存储目录内，两个不同条目的服务端文件名相同（例如不同子目录里的 `video.mkv`），且两个 Worker 同时收尾；或者同名文件与 `(2)` 至 `(99)` 均已存在。
- 预期：每个下载独占一个最终文件，不覆盖先前下载的内容。
- 实际与根因：先 `exists()` 找空位再 `renameTo()`，两步间没有占位或互斥。两个任务可以选中同一路径，后一次重命名覆盖前一个文件，两条数据库记录却都指向它。编号达到上限时，循环直接返回已存在的 `(99)` 路径，同样会覆盖。
- 验证：隔离临时目录内，用与 Kotlin 相同的 `java.io.File` API 和等价命名逻辑分别构造两个场景；两次重命名都成功，前一份内容被后一份替换。探针只证明文件操作与命名算法的组合行为，不声称完成了 Android 并发压力测试。
- 修复方向：以条目/媒体源 ID 保证最终路径唯一，或对选名与发布文件实行可靠的排他保护；编号耗尽必须明确失败，不能返回已占用路径。
- 建议回归：不同条目同名并发下载、字幕同名、编号耗尽、重复任务与中断后恢复；核对文件内容及数据库指向。

## JD-003 [P2] 同步失败被标成成功，当前进程内也不会重新调度

- 确认程度：完整调度与异常处理调用链静态确认；未向服务端发请求。
- 位置：[SyncWorker.kt · 89](/Users/torahli/github/JellyDroid/core/src/main/java/dev/jdtech/jellyfin/work/SyncWorker.kt:89) 吞掉异常，`:65` 始终返回成功；[BaseApplication.kt · 134](/Users/torahli/github/JellyDroid/app/phone/src/main/java/dev/jdtech/jellyfin/BaseApplication.kt:134) 至 `:145` 仅在 Application 启动时创建一次性任务。
- 触发：启动同步时网络已连接，但 Jellyfin 暂时不可用、请求超时或返回错误；或者启动时同步已结束，随后本地写入才产生新的待同步数据。
- 预期：暂时失败的数据可在条件恢复后重试，后续新增待同步数据也有任务负责处理。
- 实际与根因：请求失败后脏标记虽然保留，Worker 仍返回 `Result.success()`，WorkManager 不会按失败重试。全局调用搜索确认同步只由 Application 的一次性请求入队；Repository 写脏标记、恢复联网等路径没有再次调度。服务器恢复可用后，当前进程持续存活期间数据可以一直不回传，通常要等下次进程重建再试。
- 修复方向：写入待同步数据时触发受网络约束的唯一任务，并对可重试失败返回 `Result.retry()`；明确处理认证错误和部分成功，避免因任意失败导致整批无期限重传。
- 建议回归：启动成功后再新增离线修改、初次同步失败后服务恢复、部分条目失败、网络切换及进程重建。
